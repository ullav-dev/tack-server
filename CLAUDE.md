This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**tack-server** is the backend for **Tack**, a standalone Notes & Pages content platform for the Ullav ecosystem — see `/Users/colin/github/CLAUDE.md` for full workspace context.

Tack provides two content types on one shared platform:
- **Notes** — threaded, entity-attached comments/dialogs (private / team / global visibility), markdown as the canonical source of truth.
- **Pages** — Confluence/Notion-class hierarchical long-form documents, organized into spaces, with live (never denormalized) cross-references into other Ullav apps. Canonical storage is a Yjs CRDT document, enabling real-time collaborative editing; markdown/plaintext is generated on demand for search, API responses, and export.

This is currently **Phase 1**: build the server and its dedicated UI (`tack`) standalone, proven out in isolation. No existing Ullav app/service is being modified or migrated onto Tack yet — that is a separate, later phase.

## Tech Stack

- **Language:** Rust, `axum` 0.7 (matches `ullav-dam-server`'s stack exactly: `tokio-postgres`+`deadpool-postgres`, `utoipa`+Swagger UI at `/docs`, `ullav-mcp-auth` for JWT validation)
- **Database:** Postgres — raw SQL only, no ORM. Migrations live in `migrations/*.sql`, embedded at compile time (`include_dir!`) and applied on every startup in filename order (`src/db/mod.rs`; query modules live alongside it, e.g. `src/db/notes.rs`) — **every migration file must be safe to re-run** (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, etc.). This matches `ullav-dam-server`'s convention, not `ullav-user-management`'s separate `migrate`-sidecar + `schema_migrations`-tracking-table convention.
  - **Local-dev gotcha:** `include_dir!` embeds `migrations/` at compile time, but Cargo doesn't always notice a `.sql`-only change as a reason to recompile `db.rs` (observed directly while building this schema — a `cargo build` after adding new migration files finished suspiciously fast and silently ran against a stale, empty embed). If you edit *only* files under `migrations/` and the app doesn't seem to pick them up, `touch src/db.rs` (or `cargo clean -p tack-server`) before rebuilding.
  - **Tenant partitioning:** every tenant-scoped content table (`notes`, `note_bodies`, `note_revisions`, `content_attachments`, `content_references`, `spaces`) is `PARTITION BY HASH (organization_id)` into 32 fixed buckets, from the very first migration — Postgres requires the partition key in every primary key, and in every foreign key referencing a partitioned table, so every one of these tables carries `organization_id` even where it isn't otherwise needed, and FKs are always composite `(x_id, organization_id)`. Verified empirically (composite FKs, self-referential FK on `notes.parent_id`, cascading deletes, `ltree` ancestor queries, idempotent re-application) before writing the migration files — see `migrations/001_notes.sql`'s header comment. `content_attachments`/`content_references` deliberately have **no FK** to notes/pages (content is polymorphic — note or page — and can also reference entities in other services' databases entirely); that's an application-layer integrity concern, same as awe-server's own notes table.
  - `outbox_events` is a plain (non-partitioned) table for now — it's a queue, not a data store, and time-range partitioning can be added later without the one-way-door risk the content tables' hash-partitioning carries.
- **Search:** OpenSearch (secondary, rebuildable index — Postgres remains the source of truth). `src/search.rs` is a small hand-rolled `reqwest`-based REST client (not an OpenSearch SDK crate — the surface used is tiny), shared by `tack-server` (the `GET /search` endpoint) and `tack-indexer` (the outbox worker, see below). Search is **hybrid**: a BM25 lexical query and a kNN semantic query (both ACL-filtered) are combined via Reciprocal Rank Fusion (`reciprocal_rank_fusion` in `src/search.rs`), deduping a note's multiple chunk documents down to one representative result. **Multilingual analysis is not fully wired up**: the mapping's `text` field uses the default `standard` analyzer (the `analysis-icu`-backed multilingual sub-field described in the architecture plan needs that OpenSearch plugin installed, which a vanilla `opensearchproject/opensearch` image doesn't have) — but the embedding model itself (`multilingual-e5-small`) is genuinely multilingual by training, so semantic search isn't purely English-only even without ICU.
- **Embeddings:** `src/embeddings.rs` — self-hosted, local inference via `fastembed` (`multilingual-e5-small`, 384-dim, ONNX Runtime under the hood via `ort`), not an external API — per the standing decision to keep semantic search self-hosted. `Embedder::embed_query`/`embed_passages` apply E5's `"query: "`/`"passage: "` prefix convention (measurably affects retrieval quality, easy to get right from the start). `chunk_text` splits long notes into overlapping word-count chunks (400 words, 50 overlap) so a chunk boundary never splits the sentence that actually answers a query; each chunk becomes its own OpenSearch document (`note:{id}:{chunk_index}`) sharing the note's metadata. The model is loaded once at startup (`AppState.embedder: Option<Embedder>`) and cached to `EMBEDDING_MODEL_CACHE_DIR` (env var, default `./.embedding-models`) — mount a persistent volume over this path in any deployed environment so it survives restarts/redeploys. **Non-fatal degrade**: if the model fails to load (no cache + no outbound internet on first run), the server/indexer log a warning and continue lexical-only — same resilience posture as OpenSearch being unreachable at startup.
  - **Docker gotcha #1 (build-time):** `rust:*-slim-bookworm` doesn't ship `g++`/`libstdc++`, which `onnxruntime` (via `ort`) and `onig` (tokenizer regex) both need at link time — `g++` is in both Dockerfiles' apt-get install list; if you see `cannot find -lstdc++` on a fresh builder image variant, this is why.
  - **Docker gotcha #2 (runtime):** the embedding model's cache directory is written by the unprivileged `tack` user, but `/app` is root-owned by default in a multi-stage build — both Dockerfiles now `RUN mkdir -p .embedding-models && chown -R tack:tack /app` before `USER tack`. Without this, the model silently fails to load in the container with a permission-denied error (caught only by actually running the built image, not by `cargo build`).
  - **Local sandbox gotcha:** a release-profile LTO link of this dependency graph (fastembed/ort/tokenizers/image) can OOM under ~2GB RAM — hit in this project's dev sandbox (colima, ~1.9GB/2 CPUs), confirmed via a scratch `CARGO_PROFILE_RELEASE_LTO=false` Dockerfile variant (never committed). GitHub Actions runners have far more RAM, so CI is expected to be unaffected — this is a local-resource-only concern, not a reason to touch the committed release profile. **A separate, unrelated issue** from the production startup OOM below: this one is a build-time linker OOM, not a runtime one.
  - **Production startup OOM (root-caused and fixed):** every node in a real deployment cluster OOM-killed the process during startup, before "Listening on" ever logged — not a runtime leak (it never reached steady state), and not fixable by moving to a bigger node ("even in isolation" against every node in the cluster). Root cause: `fastembed` 4.x's `TextEmbedding::try_new` hardcodes ONNX Runtime's intra-op thread count to `std::thread::available_parallelism()` with no way to override it. On Linux, that reads the process's CPU affinity mask via `sched_getaffinity` — under Kubernetes' default `none` CPU Manager policy (CFS quota/period throttling, not cpuset pinning, which is what most clusters actually run unless every workload has integer CPU requests=limits and Guaranteed QoS), the affinity mask is left unrestricted to the **host's full core count**, not the pod's actual `resources` allotment. On a many-core node this spun up one ONNX Runtime intra-op thread — each with its own memory arena — per host core during session creation, independent of how small the pod's real CPU/memory budget was, which is exactly why it reproduced on every node regardless of "isolation." Confirmed by reading `fastembed` 4.9.1's vendored source directly (`text_embedding/impl.rs`: `let threads = available_parallelism()?.get(); ... .with_intra_threads(threads)?`) — no config knob existed to override this in that version. Fixed by upgrading to `fastembed` 5.x, which adds `InitOptions::with_intra_threads` (confirmed via the vendored 5.17.4 source before committing to the upgrade, not assumed from a changelog) — `Embedder::new` now takes an explicit `intra_threads: usize`, wired from `Config::embedding_intra_threads` (env var `EMBEDDING_INTRA_THREADS`, default `1`, deliberately conservative — this runs off the write path, via the outbox worker or once per search query, never a hot synchronous path, so throughput was never the constraint). The 4→5 upgrade also changed `TextEmbedding::embed` from `&self` to `&mut self` — `Embedder`'s `Arc<Mutex<TextEmbedding>>` wrapper already serializes access, so this only needed `let model` → `let mut model` on the `MutexGuard` binding, not a design change. Affects both binaries (`tack-server` and `tack-indexer` both call `Embedder::new` independently) — both wired from the same `Config` field.
  - **Follow-up build failure from the fastembed 4→5 upgrade above (root-caused and fixed):** merging that fix broke the real Docker build in CI — `cargo check`/`cargo test` (dev/test profiles) stayed clean, but `cargo build --release` inside the `docker` job failed at the link step with `undefined symbol: __isoc23_strtoll`/`__isoc23_strtoull`/`__isoc23_strtol` (glibc's C23-conformance `strtol`-family variants, only exported by glibc ≥ 2.38) and `std::__cxx11::basic_string<...>::_M_replace_cold` (a libstdc++ ABI symbol newer than bookworm's GCC 12 provides), all referenced from `libort_sys` — fastembed 5.x pulls in `ort` 2.0.0-rc.13 (up from rc.9), whose prebuilt onnxruntime binary was built against a newer glibc/libstdc++ than `rust:*-slim-bookworm` (Debian 12, glibc 2.36) ships. Both `Dockerfile` and `Dockerfile.indexer` now build on `rust:1.91-slim-trixie` (Debian 13, glibc ≥ 2.38) — **and their runtime stages too** (`debian:trixie-slim`, not `bookworm-slim`): a binary linked against newer glibc symbols doesn't run on an older glibc at all, so bumping only the builder stage would trade a build failure for a runtime crash. Verified with a real local `docker build` for both Dockerfiles (not just `cargo check`, which can't catch this — the failure is specific to the `--release` link step) — confirmed the exact same failure reproduces on `bookworm`, confirmed it's gone on `trixie`, and ran the built `tack-server` image (`docker run`) to confirm it executes past ONNX Runtime initialization, not just that it links.
  - **The same host-core-count-leakage bug class, found by auditing for it deliberately, not by another production incident:** with the ONNX thread fix live, `tack-server` was still crash-looping in production — OOM-killed at only ~560Mi actual RSS, nowhere near its own 1Gi request/2Gi limit, on a node running near its total memory capacity across all pods combined. That pattern (a pod killed well under its own allotment, on a node under real memory pressure) is the Linux *global* OOM killer picking a victim by `oom_score_adj`, not a per-cgroup limit being hit — and Kubernetes computes `oom_score_adj` from how large a pod's memory *request* is relative to the node, not its actual usage, so a pod with a comparatively small request is a preferred victim independent of whether it's anywhere near that request. `tack-indexer` — same crate, same embedding model, same `Config` — stayed stable throughout, which is the tell that the difference is actual memory *used*, not a per-request ceiling either one could hit. Audited every other place in this codebase's dependency graph for the exact same `available_parallelism()`/`num_cpus()`-reads-the-host's-core-count pattern already confirmed once (see the embeddings entry above) and found two more, both real, and both explaining why `tack-indexer` runs noticeably leaner than `tack-server` under real load despite an identical unpatched ceiling: `tack-server` actually *exercises* both (concurrent HTTP+MCP request handling), while `tack-indexer`'s single-worker poll loop rarely does:
    - `#[tokio::main]`'s default multi-thread runtime sizes its worker pool to `available_parallelism()` — each worker is its own OS thread (2MiB default stack) plus scheduler queues, real memory with no relationship to this service's actual concurrency needs. Fixed by dropping the macro for both binaries: `fn main()` loads `Config` synchronously (no runtime needed yet), then builds the runtime by hand via `tokio::runtime::Builder::new_multi_thread().worker_threads(cfg.tokio_worker_threads)`, then `.block_on(run(cfg))` — `Config::tokio_worker_threads`, env var `TOKIO_WORKER_THREADS`, default `4`.
    - `deadpool_postgres`'s own default pool ceiling (used if `create_pool` left `PoolConfig` unset, which it did) is `num_cpus::get() * 2` — confirmed by reading `deadpool` 0.12.3's vendored source directly (`util::get_default_pool_max_size`), not assumed. On a many-core node this ceiling could be 60-100+; unlike the two fields above, this one only matters under real concurrent load (an idle pool doesn't pre-open connections), which is exactly why `tack-indexer` — real DB access, but essentially never concurrent — never showed elevated memory from the identical default `tack-server` had. `db::create_pool` now takes an explicit `max_size: usize` (`Config::db_pool_max_size`, env var `DB_POOL_MAX_SIZE`, default `10`) — both binaries' call sites updated, plus the one test call site in `notes_acl.rs`.
    - Verified: `cargo check`/`cargo test --lib` (all 21 tests) clean, and both binaries run locally through to their expected first-real-error point (a DB connection failure against a deliberately bogus `DATABASE_URL`) — confirming the manually-built runtime and the capped pool actually work, not just that they compile. **Could not verify against the real cluster** — no access to it from here; this is root-caused from the same evidence class as the ONNX fix (vendored source reads + the reported symptoms matching exactly), not an empirical repro-then-fix against production.
- **`tack-indexer`** (`src/bin/tack-indexer.rs`): a second binary in this same crate (not a separate Cargo workspace member — `src/lib.rs` exposes `auth`/`config`/`db`/`error`/`models`/`search`/`AppState` so both binaries share the same code), deployed as its own container/process (`Dockerfile.indexer`) so indexing load never competes with the API server. Drains `outbox_events` via `SELECT ... FOR UPDATE SKIP LOCKED` inside a transaction held open across the OpenSearch calls for that batch — an explicit, documented trade-off (Postgres row locks held during a few HTTP calls) that's fine at today's single-worker scale and is exactly what makes it safe to later run >1 worker without double-processing. Wake-up is a fixed 2s poll, not `LISTEN`/`NOTIFY` yet — a latency optimization deferred, not a correctness gap.
- **Auth:** `ullav-mcp-auth`'s shared JWT `TokenValidator`, issued by `ullav-user-management` — same pattern as every other first-party Ullav service. `src/auth.rs`'s `TackUser` extractor (an axum `FromRequestParts` impl, mirroring `ullav-dam-server/src/auth.rs`'s `AuthUser`) decodes the caller's JWT, exposing `user_id`, `is_admin`, and **every** team the caller belongs to (with each team's `organization_id`, from the Organizations migration in `ullav-user-management`). `auth::from_mcp_claims` builds the same `TackUser` from an MCP token's claims, reusing the identical logic (`build_tack_user`) — REST and MCP enforce exactly the same rules.
  - **No per-team `tack` product-slug gate, unlike every other first-party Ullav app (Togra/Cunav/Cartlann/Lagan still gate their own).** `build_tack_user` originally filtered a caller's teams down to only those with `"tack"` in that team's `products` claim, rejecting (403) a non-admin caller with no Tack-enabled team at all. Removed deliberately, not an oversight: Tack now backs Notes/Pages for every one of those other apps, so it stopped being an opt-in product a team separately chooses to adopt and became load-bearing shared infrastructure underneath products they'd already adopted — gating it the same way meant a team could be fully onboarded to (say) Cunav and still get a blanket 403 from every Tack-backed Notes call the moment that call reached tack-server, for no reason visible from Cunav's own side at all. The **only** thing this change touches is whether a caller gets a `TackUser` in the first place (still requires being an admin, or belonging to at least one team, any team). It does not touch, weaken, or bypass **any** actual content-visibility decision — `notes_acl.rs`'s private/team/organization visibility and `pages_acl.rs`'s live ancestor/space-permission resolution are both completely unrelated code paths, resolved fresh per-request exactly as before, and neither one ever consulted the product gate to begin with. A team with no `tack` product row can now reach the API at all, but still only ever sees the same notes/pages that visibility model would have shown them regardless. No backfill script needed or written — the preferred fix was removing the gate outright, not granting it retroactively to every existing team, since the gate itself no longer represents a real access decision.
- **MCP:** `src/mcp/server.rs` — `rmcp`-based Streamable HTTP server at `/mcp`, gated by `mcp_auth_middleware` (audience-bound RS256) + a `tack:tools` scope guard, same shape as `ullav-dam-server`'s MCP server. Tools are outcome-shaped, not 1:1 REST mirrors (matches Obair's `get_task_context` precedent): `search_content`, `get_note_thread` (a note + its full reply thread in one call), `create_note`, `reply_to_note`. Requires `ullav-user-management` PR #59 (adds the `tack` MCP resource gate to the `client_credentials` grant — without it, a tack MCP token request on the default port 8087 would be silently gated against Cartlann's `collection` product instead, since both services default to that port).
  - **`jsonwebtoken` `CryptoProvider` panic on every authenticated request (root-caused and fixed):** every real client of `tack-server` (the Tack frontend, MCP callers) got a hard failure on any route that decodes a JWT — `TackUser` extraction or the MCP auth middleware — while `GET /health` (no auth) stayed fine, which was the tell it was auth-path-specific rather than a general server fault. The actual failure was a panic inside `jsonwebtoken::crypto::verify`, not a normal `Result::Err` — axum has no panic-catching layer here, so the connection just died; what looked like "HTTP 500" from the Tack app was that app's own proxy turning the failed upstream fetch into a 500, not a status this server ever returned deliberately. Root cause, confirmed by reading the vendored `jsonwebtoken` 10.4.0 source (`src/crypto/mod.rs`): starting with 10.x, `jsonwebtoken` picks its crypto backend the same way `rustls` does — by requiring *exactly one* of its `rust_crypto`/`aws_lc_rs` Cargo features to be enabled process-wide, auto-selecting only in that unambiguous case. `ullav-mcp-auth` requests `rust_crypto`, but this crate's own `surrealdb` dependency (present only for the `backfill-clann-notes` binary, see that binary's doc comment) transitively pulls in `jsonwebtoken` with `aws_lc_rs` enabled — and because both crates resolve to the *same* `jsonwebtoken` version, Cargo unifies their features onto one shared build, enabling both backends at once. With neither backend exclusively enabled, `jsonwebtoken`'s internal `CryptoProvider::from_crate_features()` falls through to a stub provider whose `signer_factory`/`verifier_factory` just `panic!()` on first call — invisible to `cargo build`/`cargo test` (feature resolution isn't a compile error), only surfacing at runtime on the first JWT verify. Fixed by installing the same backend `ullav-mcp-auth` was built and tested against, explicitly and unambiguously, as the very first thing in `main()` (before the tokio runtime is even built, so no thread can race it): `jsonwebtoken::crypto::rust_crypto::DEFAULT_PROVIDER.install_default()`. Required adding `jsonwebtoken` (`rust_crypto` feature) as a direct dependency of `tack-server` itself, purely so this call site has something to name — it does not otherwise touch JWT logic, which still lives entirely in `ullav-mcp-auth`. Verified end-to-end against real infrastructure, not just "doesn't panic at startup": minted a real RS256 token from a running `ullav-user-management` (`POST /auth/login`), confirmed `GET /me` returns `200` with correctly decoded claims and no panic in the log (an invalid/malformed token alone doesn't prove this — `jsonwebtoken::decode` rejects those during header parsing, before ever reaching the code path that was actually panicking).
- **Dev port:** 8087 (reserved; matches `tack` frontend's `API_URL` default)

## Pages (schema + CRUD + ACL only — step 8a; real-time collab is a later step)

`migrations/004_pages.sql`: `pages`, `page_docs`, `page_permissions` — organization-hash-partitioned into 32 buckets, same as every other content table. `pages.path` is a materialized `ltree` path (`p1.p2.p3`), the exact same technique as `notes.thread_path`: a single indexed ancestor-path query resolves "the nearest ancestor with an explicit permission override" without an N-hop `parent_id` walk. `spaces` (from `001_notes.sql`) is the tree's root container — a space's own `team_id` (nullable, org-wide if absent) is the fallback membership check when no page in the ancestor chain has an override.

- **Content storage is plain markdown for now, not Yjs.** `page_docs.content_markdown` is the write path — pages are created/edited through this REST API only (single-writer, no live co-editing). `page_docs.yjs_doc_state` exists as a column but stays `NULL` until a later PR introduces the Hocuspocus real-time sync server, at which point it becomes the source of truth and `content_markdown` becomes a derived projection of it. This column was added now specifically so that transition is additive, not a schema-breaking migration.
- **Permissions are resolved live, every request, in `src/pages_acl.rs`** — never denormalized or copied onto children. Resolution order: (1) admins always get `Edit`; (2) if the nearest ancestor-or-self page (walking up `path`) has any `page_permissions` rows, those rows are an **exhaustive whitelist** — the caller's level is whatever those rows grant, or no access at all if they aren't listed, even if they'd otherwise qualify via space membership. This does not fall through further — matching how Confluence restrictions actually behave, not a partial/additive composition; (3) if no ancestor in the chain has any override, fall back to space membership (team members get `Edit` by default; an org-wide space, `team_id IS NULL`, is open to any org member). This is the direct structural fix for Confluence's documented bug where restrictions are copied once at creation time and silently go stale when a parent's permissions later change.
- Two permission levels only, `view`/`edit` — matching Confluence's actual page-restriction model, not a made-up finer-grained scheme. A `comment` tier is deferred, not designed away.
- REST surface: `POST`/`GET`/`PATCH /spaces` (rename reuses `pages_acl::can_create_in_space`'s "space default Edit level" check -- same rule that already gates creating a root page, since there's no finer-grained space-level permission model), `GET /spaces/:id/pages?parent_id=` (direct children, or root pages if omitted — each candidate's permission is resolved individually, since a child can be more or less restricted than its siblings), `POST /pages`, `GET`/`PATCH`/`DELETE /pages/:id`, `GET /pages/:id/permission` (the caller's own effective `view`/`edit` level — exists specifically so [`tack-hocuspocus`](https://github.com/ullav-dev/tack-hocuspocus) can delegate ACL resolution back here instead of reimplementing `pages_acl` in TypeScript, also useful to the frontend directly), `GET`/`POST /pages/:id/permissions`, `DELETE /pages/:id/permissions/:permission_id`.
- **List pagination**: `GET /notes`, `GET /note-folders`, `GET /spaces`, and `GET /spaces/:id/pages` all take `limit`/`offset` and return a `total`, on the standing rule that a list gets built scale-safe by default rather than judged "probably small enough to skip." `GET /spaces/:id/pages` is the one with a real internal tradeoff: since each candidate page's permission is resolved live and per-row (`pages_acl::resolve_effective_permission`, same limitation `handlers::search::search` documents for page search hits), a true SQL `LIMIT`/`OFFSET` would paginate *before* that filter removes rows and undercount a page. So it fetches every direct child of `parent_id` (bounded by realistic authoring -- Confluence itself doesn't paginate one page's children either, for the same structural reason), resolves each one's permission, then slices the *visible* set for `limit`/`offset` in Rust. The API contract is identical to the other three lists; only the implementation fetches more than one page's worth internally. `GET /note-folders` and `GET /spaces` paginate *within* each of the caller's organizations and sum the totals (same per-organization-loop shape every other multi-org list in this API already has) rather than merging into one globally-ordered page across organizations -- a documented tradeoff for a case (a caller's folders/spaces split across orgs) this API doesn't otherwise handle specially anywhere.
- Creating a root page checks the caller has `Edit` on the *space* (`pages_acl::can_create_in_space`, since there's no page yet to hold an override); creating a child page checks `Edit` on the *parent page* (which itself resolves through the same live ancestor-or-space-fallback logic).
- Cascading **hard** delete via FK works correctly (verified: deleting a page cascades to its children, `page_docs`, and `page_permissions`; deleting a space cascades to its pages). Soft-delete (`DELETE /pages/:id`) only soft-deletes the single target page — cascading the soft-delete to descendants is a documented, deliberate simplification for this pass, not a data-integrity gap (a hard delete of the page or its space still fully cascades).

**Verified live with two genuinely distinct, separately-authenticated real users** (not just unit tests): created a space + a 3-level page tree (root → child → grandchild) as an admin, restricted the child page to an unrelated fake user id (view-only), then logged in as a freshly created, separate non-admin team member and confirmed: they could view/edit the *unrestricted* root page via space-default `Edit`; they got a clean `403` on the *restricted* child; they also got `403` on the *grandchild* (proving live ancestor-inheritance actually works over the wire); and the restricted child was correctly excluded from `GET /spaces/:id/pages?parent_id=<root>` for that same denied user. The ancestor-permission-resolution SQL query was also prototyped and confirmed against a real Postgres instance *before* any Rust was written.

**Yjs/Hocuspocus real-time collaborative editing is implemented** as a separate service, [`tack-hocuspocus`](https://github.com/ullav-dev/tack-hocuspocus) (Node/TypeScript — the first non-Rust backend service in this org, since Hocuspocus is TipTap's own reference sync server, not reimplemented from scratch). It authenticates each connection by calling `GET /pages/{id}/permission` here (forwarding the connecting user's own token), and persists/loads `page_docs.yjs_doc_state` via its own direct Postgres connection — see that repo's `CLAUDE.md` for the full design. `page_docs.content_markdown` **is now kept accurate** by that same service (its `onStoreDocument` hook derives Markdown from the Yjs doc on every save) — the earlier "goes stale after a collaborative edit" gap is fixed. That still doesn't reach OpenSearch, though (see below) — `content_markdown` being fresh in Postgres and a page showing up-to-date in search are two different, separately-solved problems.

**Named-snapshot Page version history (step 8c) is implemented**: `migrations/007_page_revisions.sql` (`page_revisions`, org-hash-partitioned exactly like `note_revisions`) + `POST`/`GET`/`DELETE /pages/{id}/revisions`. Same explicit-only trigger model as Notes (confirmed with Colin before building, since the plan's original text described *automatic periodic* snapshots for Yjs-bloat/GC purposes — a genuinely different, still-unaddressed concern this table does **not** solve): a version is only ever created by an explicit `POST`, never implicitly. Stores `content_markdown` (not a Yjs binary snapshot) — simple, human-readable, view-only history, no "restore into the live Yjs doc" feature, matching Notes exactly. Unlike Notes, there's no automatic baseline revision at page-creation time and no "can't delete the last remaining version" guard — a page can validly have zero revisions until someone explicitly saves one, and deleting down to zero is not a special case.

**Page-to-page cross-references (step 8d) are implemented, scoped to page-to-page only for this pass** — confirmed with Colin first: true cross-*service* resolution (a Togra workflow ref, a Cunav ticket ref) needs a new public resolve endpoint in the *owning* service (e.g. `awe-server`), which doesn't exist yet (only internal-only helpers like `awe-server/src/numbering.rs`'s `parse_task_ref`/`resolve_workflow_by_ref` do — real, designed-but-unbuilt prior art per the plan, not a false lead — but nothing public to call). This uses the same generic `content_references` table (present since migration 002, unused until now) with `owning_service = 'tack'`, `entity_type = 'page'`. `GET /pages/search?space_id=&q=` (plain `ILIKE` title search, org-wide not space-scoped — a title search doesn't need OpenSearch) backs the reference picker. `POST`/`GET`/`DELETE /pages/{id}/references` (a page's own outgoing references) and `GET /pages/{id}/backlinks` (the reverse — pages that reference this one, doubling as the backlinks UI per the table's original design) always resolve the *other* page's title live, never denormalized — a reference to a since-deleted or now-inaccessible page comes back with `target_title`/`source_title: null` (a "broken link" state the UI can show), not an error. Verified live: created two real pages, searched by title, created a reference, listed it both directions (outgoing from the source, as a backlink on the target), deleted the target page and confirmed the reference resolves to `null` rather than erroring, then deleted the reference row itself and confirmed a second delete 404s.

**Page content indexing into OpenSearch is now implemented.** `tack-indexer`'s `apply_event` previously no-opped on every `content_type = 'page'` outbox event — Pages were never actually wired into search at all, a bigger gap than the repo's earlier notes implied. It now mirrors the Notes path: `search::index_page`/`delete_page` chunk and (re-)index/remove a page's `content_markdown` the same way Notes' body is handled. The one structural difference: Notes' visibility enum is fully expressible as a static OpenSearch query filter (`SearchCaller::acl_filter`), but Pages' ACL is resolved live from the page/space tree (`pages_acl.rs`) and can't be. `acl_filter` only applies a coarse "belongs to one of the caller's organizations" pre-filter for pages; `handlers::search::search` then live-rechecks every page hit via `pages_acl::resolve_visible_page` (the same function `GET /pages/:id` and `GET /pages/search` already use) before returning results, skipped entirely for admins. Companion fix in `tack-hocuspocus` (its own PR): `onStoreDocument` now enqueues an `outbox_events` row in the same transaction as its `page_docs` write, so a purely-collaboratively-edited page gets (re-)indexed too, not just REST-API-written ones. Verified live: created a page via REST, watched `tack-indexer` drain the resulting event and index it, found it via `GET /search` (ranked above unrelated notes/pages), soft-deleted it, watched it disappear from search results too.

**Search overhaul (Phase C of the Navigator redesign)**: the original implementation returned unlabeled raw body chunks with no title, no highlighting, no way to link a page hit at all (`SearchHit` had no `space_id`), and a reply hit linked to itself instead of its thread. All fixed:
- The index mapping (and `index_note`/`index_page`) gained `title`, `folder_id`/`parent_id` (notes), `space_id` (pages) — already-present fields on `Note`/`Page`, no model change needed. A reply hit's `parent_id` is what lets the frontend link to `/notes/{parent_id}` (the actual thread) instead of the reply's own id, which has no useful standalone view.
- Both sub-queries (lexical + kNN) now request OpenSearch's own `highlight` (on `text`), so a hit shows `<em>`-wrapped matched fragments, not a raw ~400-word chunk. Falls back to the plain `text` prefix for a pure-semantic kNN match sharing zero literal terms with the query.
- `GET /search` now returns `SearchResults { notes: SearchTypeResults, pages: SearchTypeResults }` — grouped by type, each independently paginated (`notes_limit`/`notes_offset`/`pages_limit`/`pages_offset`, default 10, max 50) — confirmed design: search stays global across both types regardless of which Navigator tab is active. Pagination happens in `handlers::search::search`, *after* the page-ACL post-filter, not inside `SearchClient::search` — paginating the fused list first could hand back a page that's short real results once invisible pages are filtered out. Each raw sub-query now fetches up to `RAW_FETCH_SIZE` (200, up from 50) candidates before RRF fusion/dedup, comfortably covering several pages of *deduped* results — not an attempt at exhaustive pagination over every matching document, which no search engine does either.
- `tack-indexer --backfill`: a rerunnable one-shot mode (not a new binary) that walks every non-deleted note and page and re-indexes it — a new indexed field never retroactively populates already-indexed documents, so without this the title/highlight improvements above wouldn't show up for existing content until it happened to be edited again. `db::notes::list_all_for_backfill`/`db::pages::list_all_for_backfill` (plain `LIMIT`/`OFFSET`, cross-organization — an occasional maintenance walk, not a hot path).
- **Bug found and fixed via live backfill testing, not by inspection**: `delete_note`/`delete_page`'s `_delete_by_query` calls now pass `?conflicts=proceed`. The default (`conflicts=abort`) aborts the *entire* delete the moment any one matched document's seqNo has moved since the query's internal search phase (observed live: pages with empty content consistently 409'd against docs genuinely present in the index) — `proceed` skips conflicting documents instead, which is correct here since every caller already treats "nothing left to delete" as success, and a lost race gets cleaned up by that content's own next index/delete event or the next backfill run regardless.

**Search scoped to one team (follow-up fix, post-overhaul)**: `GET /search` originally searched across *every* team/org the caller belonged to, unlike every other list endpoint in this API (`GET /notes`, `GET /note-folders?team_id=`) — a hit from an unrelated team could surface with no indication why, which read as a visibility bug even though the underlying per-note ACL enforcement (`SearchCaller`'s should-clauses) was always correct. `team_id` is now a **required** query param (mirrors `GET /notes?team_id=`), resolved via `notes_acl::resolve_team_organization` — the same membership check every other team-scoped write already uses, including for an admin caller, who must still actually belong to the team being searched (an admin was never exempt from `GET /notes`' own `team_id` filter either). `SearchCaller` shrank from `Vec<Uuid>` team/org lists to single `team_id`/`organization_id` fields, and its old `acl_filter() -> Option<Value>` ("`None`" meaning admin-sees-everything, unscoped) became `filters() -> Vec<Value>` — always at least the team/org scope clause, admin or not; only the *visibility* clause (private/team/organization) is skipped for admins now, not the team scope itself. Notes are scoped by their own indexed `team_id`; pages have no `team_id` field indexed (only `organization_id`/`space_id`), so page hits stay scoped by the requested team's organization only — deliberately not extended to per-page team scoping in this pass, since `GET /spaces` itself still isn't team-scoped either (a separate, explicitly deferred inconsistency, not fixed here). The MCP `search_content` tool gained the same required `team_id` param, for parity with the REST endpoint.

**Two search-quality bugs found and fixed live, via direct measurement against real dev data, not by inspection**:
- **Stale `folder_id` in search results**: `db::notes::update_note` only enqueued an outbox re-index event when title/body/visibility changed — a folder-only `PATCH` (file/move/unfile) never did, a leftover assumption from before `folder_id` was added to the search index mapping ("folders aren't searchable content"). Filing a note found via search into a folder, then re-searching, kept showing it as unfiled, even after the note's own folder actually changed correctly in Postgres. Fixed: `new_folder_id.is_some()` now also triggers the outbox event, same as any other field change.
- **Irrelevant kNN noise on short/low-information queries** (e.g. searching "44" or "abx" surfaced a pile of unrelated notes/pages): two compounding causes, both confirmed with a throwaway live script before touching any code.
  1. `chunk_text("")` returns *one* chunk holding an empty string, not zero chunks — a wrong assumption `index_page` was built on. It indexed that empty-text chunk (with a real, meaningless embedding) unconditionally, then tried to delete it via `delete_page` in the same call — a real race against OpenSearch's near-real-time refresh (~1s default): the delete's internal search phase can run before the just-written doc is visible, finding nothing to delete and orphaning it permanently. Several genuinely empty pages had exactly this: a `text: ""` document sitting in the index indefinitely. Fixed: `index_page` now filters out empty/whitespace-only chunks *before* indexing anything, and skips straight to `delete_page` (cleaning up any stale prior chunks) when nothing real is left — never creates the empty document in the first place, so there's no race to lose.
  2. Even after that cleanup, kNN itself is close to meaningless on very short/low-information queries with `multilingual-e5-small`: measured live, cosine similarity for "44"/"abx" against the whole corpus clustered in a tight ~0.90-0.94 band *regardless of actual relevance* — a completely unrelated wiki page scored higher than some genuine matches. No absolute or relative score threshold cleanly separates signal from noise in that band. Lexical (BM25) alone, measured the same way, got both queries exactly right (found the one real "44" mention, found zero "abx" matches, correctly — there is no such text in the corpus). Fixed: `SearchClient::search` now skips the kNN sub-query entirely below `MIN_SEMANTIC_QUERY_CHARS` (4), falling back to lexical-only for short queries, where lexical is already both correct and sufficient. A longer query still gets the full hybrid treatment.

**Explicitly deferred**: extending team-scoping to `GET /spaces` (currently returns spaces across every team/org the caller belongs to, with no `team_id` param at all — flagged directly to Colin, kept as-is deliberately for this pass rather than folded in as a side effect of the search fix); true cross-service reference resolution (needs a new public endpoint in each owning service, starting with `awe-server`); periodic automatic Yjs-bloat-management snapshots (distinct from `page_revisions`, see above); multilingual ICU analysis for the lexical side of Page search (same pre-existing gap as Notes, see "Search" above); a searchable folder-name resolution for note hits (frontend resolves `folder_id` to a name client-side from its own already-fetched folder list, not a backend join).

## Notes folders

`migrations/008_note_folders.sql`: `note_folders` -- a flat (non-nested), per-team grouping for *top-level* notes only, org-hash-partitioned into 32 buckets like every other content table. `notes.folder_id` (nullable) is enforced top-level-only by a DB `CHECK` constraint (`parent_id IS NULL OR folder_id IS NULL`) -- a reply can never be independently filed, only its parent thread can. The composite FK (`notes_folder_id_fkey`) deliberately carries **no** `ON DELETE` action: a composite `ON DELETE SET NULL` would try to null `notes.organization_id` too (it's part of the FK) and violate that column's own `NOT NULL` constraint. Instead `db::note_folders::delete_folder` explicitly unfiles every note in the folder (`folder_id = NULL`) in the same transaction before deleting the folder row -- a note is never deleted along with its folder, only ungrouped.

Folders carry no visibility/ACL of their own -- they're an organizational tool, not access-controlled content. Any member of the folder's `team_id` may create/rename/delete it (`handlers::note_folders::resolve_folder_for_caller`); each note's own `Visibility` still governs who can see it once inside. `GET /notes?team_id=` gained optional `folder_id=`/`unfiled=` params (mutually exclusive); omitting both preserves the original unfiltered behavior exactly, so no existing caller (the frontend's `NotesList.tsx`, the MCP `search_content`/`get_note_thread` tools) needed to change. `PATCH /notes/{id}` gained a tri-state `folder_id` field (omit = unchanged, `null` = unfile, a value = file/move) via a `deserialize_some` double-`Option` wrapper, since ordinary `Option<T>` can't distinguish "omitted" from "explicitly null." No outbox events are enqueued for folder CRUD or for a folder-only note PATCH -- folders aren't indexed/searchable content, so there's nothing for `tack-indexer` to do with that event.

REST surface: `POST`/`GET /note-folders`, `PATCH`/`DELETE /note-folders/{id}`. No MCP tool exposes folders yet (out of scope for this pass -- `create_note`/`reply_to_note` are unaffected, just pass `folder_id: None`).

Verified live against a real Postgres instance (a throwaway `db::` call script, not committed): created a folder, filed a note into it at creation time, listed it both folder-scoped and unfiled-scoped (confirming mutual exclusivity), moved it out and back in via the tri-state PATCH semantics, confirmed an unrelated title-only edit leaves `folder_id` untouched, renamed the folder, then deleted it and confirmed the note survives, unfiled, rather than being deleted along with its folder.
